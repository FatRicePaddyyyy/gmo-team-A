## 01. ハッカソン概要

### 1.1 ゴールと進め方

**概要**: EPPベースの疑似レジストラサービスを、Claude Code等によるAI駆動開発でチーム制作する5日間プログラム

**ゴール**
- EPPを用いた疑似レジストラアプリを完成させる
- 単なるコーディング補助でなく、AIエージェントに設計〜実装を委任する開発を体験する

**進め方**
- チーム制（要件定義→設計→実装→テスト→発表）

- Claude Code等のAIエージェントを使った開発プロセス

> **POINT**: 「AIにコードを書かせる」だけでなく、要件整理・設計判断・レビューまでAIと協働するエージェント型の開発を体験することが目的

## 02. ドメイン基礎知識

### 2.1 IPアドレスとドメイン

Webサイトを開く・メールを送信するには、インターネットを通じてどのサーバーにアクセスするか特定する必要がある。

```
ユーザー（www.onamae.com と検索）
  → DNSサーバー（ドメイン名 → IPアドレスを応答）
  → Webサーバー（210.172.128.200）
```

- **DNS（Domain Name System）**: ドメイン名とIPアドレスを紐づけて変換する仕組み。インターネットの「電話帳」のような役割
- **DNS階層構造**: ルートDNS（.）→ TLD DNS（.com等）→ 権威DNS

> **POINT**: IPアドレスは覚えにくいため、人間が扱いやすい文字列（ドメイン）に変換する仕組みがDNS

### 2.2 ネームサーバーと委任

名前解決は、上位ゾーンから順に「どの権威DNSが担当か」を辿る＝委任（Delegation）の連鎖

```
ルートDNS（.）
  → 上位DNS（.com）「.com」の一覧を管理
  → 権威DNS（ns1/ns2.onamae.ne.jp）ゾーン（A/MX/TXT等）を保持
  → Web／メールサーバー（IPを返答）
```

**委任（Delegation）の要点**
- 委任＝上位ゾーンが「下位ドメインの権威DNSはどれか」を指し示すこと
- ドメイン登録時にNS（例：ns1.onamae.ne.jp）を上位DNS側へ登録 → 上位ゾーンに委任情報（NSレコード）が載る
- お名前.comはレンタルDNSとして権威DNSを提供。NSを変更すると使用する権威DNS（ゾーン）が切り替わる

### 2.3 DNSレコードの種類

権威DNS（ゾーンファイル）に登録される設定情報。お名前.comのレンタルDNSでは管理画面から設定できる。

| レコード | 役割 |
|---------|------|
| A / AAAA | ホスト名 → IP |
| CNAME | 別名 |
| MX | メール配送 |
| NS | 権威DNS指定 |
| TXT | 認証用文字列 |

### 2.4 TLD（トップレベルドメイン）

ドメイン名をドットで分割した際の最後の部分。例：www.gmo.jp → `.jp` がTLD。2026年時点で約1,400種類以上（IANA Root Zone Database調べ）

| 種類 | 数 | 説明 | 例 |
|-----|---|------|-----|
| gTLD（分野別） | 1,200個以上 | 用途・分野別のTLD | .com, .net, .org |
| ccTLD（国別） | 約250個 | 国・地域を表すTLD | .jp, .uk, .us |
| sTLD | 約14個 | 特定組織向け | .gov, .edu |
| インフラTLD | 1個 | インフラ用 | .arpa のみ |

> **POINT**: 登録対象はSLD+TLD（例：example.co.jp）。サブドメインは登録者がDNSで自由に追加できる

### 2.5 gTLDの歴史

| 時期 | 内容 |
|------|------|
| 1984〜88 | 7種類のみ（com / net / org / edu / gov / int / mil） |
| 2000 | 7種類追加（biz / info / name 等） |
| 2012 | 新gTLDプログラムで自由化（.shop .tokyo 等） |
| 現在 | 1,200種類以上 |

> **POINT**: 2012年の新gTLDプログラム（自由化）以降gTLDは急増。用途特化型（.shop / .app 等）や地域型（.tokyo 等）など、多様化が進んでいる

## 03. ドメイン業界構造

### 3.1 ドメインの商流とプレイヤーの役割

```
IANA（技術的資源管理：IP割当・ルートゾーン・TLDの技術管理。ICANN内の一部門）
  ↓
ICANN（国際管理団体、1998年設立。レジストラ認定・gTLD承認・ポリシー策定・IANA監督）
  ↓
レジストリ（TLDごとの管理団体（卸）。ゾーン管理・配信、ユーザーへ直販不可。例：Verisign / JPRS / GMOドメインレジストリ）
  ↓
レジストラ（ICANN認定の直販事業者。レジストリと仕入交渉し1円提供も。← お名前.comはここ）
  ↓
リセラー（レジストラから仕入れて再販する代理店）
  ↓
エンドユーザー（ドメインの利用者）
```

### 3.2 レジストラの機能

レジストラが持つ主要機能 — 各操作はレジストリへのEPPコマンドで実行される

### 3.3 ドメイン移管（レジストラ間の移行）

```
レジストリ（1つ）TLDごとの登録台帳。両レジストラは同じ1つのレジストリに接続
  ↑                          ↑
レジストラA（移管元）  ←AuthCodeで本人確認→  レジストラB（移管先）
```

移管の主な動機：
1. **UI（管理画面）の使いやすさ** — 直感的で分かりやすい管理画面を求めて移管
2. **更新料金の安さ** — 他社より安価な更新料金を求めて移管

> **POINT**: レジストリは1つ。移管しても台帳は変わらず、切り替わるのは取り次ぐレジストラのみ。ICANN規定により、登録・前回移管から60日間は移管不可

## 04. ドメインのライフサイクルとEPP

### 4.1 ドメインの状態遷移

```
登録可能 → 登録済み（Active）→ 期限切れ（Expired）→ Grace Period → 登録可能（削除・再登録可能）
            [Create]                                   [AGP/Renew GP/Transfer GP等]
```

- **Grace Period（猶予期間）**: ICANNが定めたドメイン操作を取り消し可能な期間（RFC 3915）

> **POINT**: Grace Periodの長さはTLDごとに異なる。RGPからの復旧（restore）は追加費用が発生する

### 4.2 EPP概要と主要コマンド

**EPP（Extensible Provisioning Protocol）**: レジストラとレジストリ間の標準通信プロトコル

| 項目 | 内容 |
|-----|------|
| 規格 | RFC 5730（基本仕様） |
| 形式 | XML |
| 通信 | TCP（ポート700）＋TLS |

```
レジストラ → [EPP / XML over TLS ポート700] → レジストリ（Verisign 等）
```

**本ハッカソンでの注意点**: 本物のEPPはTCP接続管理・XML名前空間・TLSクライアント認証の学習コストが大きいため、本ハッカソンではトランスポートを **HTTP/REST + JSON** とする

### 4.3 EPPステータスコード

ドメインの状態を示すコード — Client（レジストラ設定）とServer（レジストリ設定）の2種類がある

> **POINT**: Serverステータスは Clientステータスより優先される

### 4.4 ドメイン登録のE2Eフロー（申込〜DNS反映）

```
① ユーザー（ドメインを検索・申込）
  → ② レジストラ（空き確認(check)→登録(create)→NS設定(update)）
  → ③ レジストリ（台帳へ登録、ゾーンファイルに反映）
  → ④ 権威DNS（世界中のDNSへゾーン情報を配信）
  → ⑤ 名前解決（キャッシュ反映後アクセス可能に）
```

> **POINT**: ②③の連携はEPPコマンド（check / create / update）で行われる。反映時間はレジストリ処理＋DNSのTTL／キャッシュに依存

## 05. 登録データとプライバシー

### 5.1 RDDS / Whois / RDAP

**RDDS（Registration Data Directory Services）**: ドメイン登録データを検索・参照するサービスの総称

- **Whois**: 従来の方式
- **RDAP**: 現行標準（2025年1月以降）
- **Whois情報公開代行**: 登録者情報を代理公開しプライバシーを保護

RDDSで参照できる主なデータ：ドメイン名・登録者・NS・登録／有効期限・ステータス

### 5.2 コンタクト情報と登録データの公開

ICANNのRegistration Data Policy（2025年8月21日発効）により、コンタクトの収集要件が再整理：

| コンタクト | 状態 |
|----------|------|
| Registrant | 必須（正確性・変更時7日以内の更新義務） |
| Technical | 任意（提供義務なし） |
| Administrative | 撤廃 |
| Billing | 撤廃 |

- 登録データは原則非公開（リダクション）
- 背景：GDPR等の個人データ保護（データ最小化）

## 06. お名前.com

### 6.1 お名前.comとは

| 指標 | 数値 |
|-----|------|
| サービス開始 | 1999年9月 |
| 国内ドメイン登録シェア | 87.5% |
| 登録件数（累計） | 4,200万件 |
| サーバー販売数（累計） | 70万件 |

### 6.2 お名前.comの強み

1. **安い** — 1円からドメイン登録OK（圧倒的最安値）
2. **早い** — 超速プライスマッチ：他社より1円でも高ければ発見から24時間以内に値下げ

> **POINT**: 圧倒的強者の戦略 — 競合から比較されず戦わずして勝つ

### 6.3 取扱いサービス一覧

| カテゴリ | サービス |
|---------|---------|
| 基本サービス | ドメイン登録・更新・移管 / Whois情報公開代行 / レンタルDNS / メール・URL転送 |
| セキュリティ・保護 | SSL証明書発行 / ドメインプロテクション / ドメインモニタリング / TMCH（商標保護） |
| 売買仲介 | ドメイン売買・オークション / バックオーダー / プレミアムドメイン |
| 広告収益 | ドメインパーキング（未使用ドメインへの広告表示） |

### 6.4 サービス詳細

| サービス | 概要 |
|---------|------|
| TMCH | 商標権者向けドメイン優先登録サービス。新TLD公開時のサンライズ期間に優先登録が可能 |
| バックオーダー | 他者保有の価値あるドメインを予約。有効期限切れ時に自動取得を試みる |
| ドメインパーキング | 未使用ドメインに広告ページを自動作成。クリック数に応じて収益を得られる |
| プレミアムドメイン | 短い・覚えやすい等、価値の高いドメインを販売 |
| ドメインプロテクション | 不正アクセス防止。設定変更時に追加認証が必要 |
| ドメインモニタリング | 自社ブランド等を含む500種以上のドメインを定期監視し、空き発生時に通知 |

### 6.5 新gTLD公開とお名前.comの優先登録

```
Phase 1（サンライズ期間）: 商標権者のみ / 高額 → TMCHによる商標優先登録
  ↓
Phase 2（ランドラッシュ）: 誰でも / 高額 → 先行予約・バックオーダー
  ↓
Phase 3（一般公開 GA）: 誰でも / 通常価格 → 通常のドメイン登録
```

## 07. システム概要

### 7.1 システム構成

```
NAVI（画面）
  ↓ API
  API
  ↓ API
  BATCH ← DB
  ↓ BRIDGE
  BRIDGE
  ↓
REGISTRY（Verisign / JPRS / GMOレジストリ / Key-Systems / GoDaddy Registry / Identity Digital / CentralNic 他）
```

**レイヤーを分ける理由**

| レイヤー境界 | 理由 |
|------------|------|
| 画面／API | APIが一時的に停止しても画面は表示継続できる。複数プラットフォーム対応もしやすくなる |
| API／BRIDGE | レジストリごとに通信仕様が異なるため、差異をBRIDGE層に閉じ込め、APIから意識せずに済むようにする |

## 08. 開発するアプリ概要

### 8.1 アプリコンセプト

ICANN認定レジストラと同様に、会員向けにドメインのライフサイクル操作を提供する「疑似レジストラサービス」を開発する

```
会員（エンドユーザー）
  → 開発するアプリ（疑似レジストラ）
  → EPP（check / create / update / renew / delete / transfer / restore）
  → Kitaqsign / Kitaqnic（疑似レジストリ）
```

**本アプリの役割**: 会員が保有するドメインの登録・更新・情報修正・廃止・復旧・移管を、Kitaqsign / Kitaqnic の疑似レジストリに対するEPPコマンドとして実行する

### 8.2 レジストリ構成とAPI仕様

**開発時の注意点**
- 2つのレジストリはAPIの提供形式（EPPコマンド相当のREST API）が異なる場合があるため、実装前に両方のSwagger UIでリクエスト／レスポンス形式・認証方式・エンドポイントを確認すること
- 実際のEPP（RFC 5730）と対応関係にあるが、疑似実装のため両ドキュメントの仕様を正とする

## 09. 必須機能（コア機能）

### 9.1 会員向け必須機能

すべての機能はKitaqsign / KitaqnicへのEPP相当コマンドとして実行される

| 機能 | EPPコマンド |
|-----|-----------|
| ドメイン検索 | check |
| ドメイン登録 | create |
| NS設定・情報修正 | update |
| ドメイン更新 | renew |
| ドメイン廃止 | delete |
| ドメイン移管 | transfer |
| ドメイン復旧 | restore |

### 9.2 機能フロー例（ドメイン登録）

```
① ドメイン検索（会員が希望のドメイン文字列を入力）[check]
  → ② 登録申込（空きを確認し、登録内容を入力）[create]
  → ③ NS設定（初期ネームサーバー等の情報を設定）[update]
  → ④ 登録完了（会員の管理画面に反映）[info]
```

> **POINT**: 廃止・復旧・移管についても、EPPのステータス・猶予期間（Grace Period）を意識した実装が求められる
